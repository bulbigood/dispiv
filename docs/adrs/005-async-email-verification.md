# ADR-005: Асинхронная верификация Email при регистрации

> **Краткая суть**: При регистрации пользователя HTTP-запрос не должен блокироваться отправкой письма. Создание пользователя и генерация токена происходят синхронно, а отправка письма делегируется асинхронному консьюмеру через Kafka.

---

## 1. Контекст и Проблема (Context & Problem Statement)

При синхронной регистрации пользователь нажимает "Зарегистрироваться", сервер создает запись в БД, а затем инициирует SMTP-сессию для отправки письма с токеном верификации.

**Проблема:**
Время отклика API деградирует из-за внешних факторов. Математически время ответа выглядит так:
$$ T_{response} = T_{db\_commit} + T_{smtp\_handshake} + T_{email\_send} $$

При нагрузке или проблемах у SMTP-провайдера (например, SendGrid), $T_{response}$ может достигать 10-15 секунд, что приводит к таймаутам на клиенте (UI показывает спиннер, пользователь жмет кнопку повторно, возникают дубликаты).

**Требование:** P99 Latency эндпоинта `/api/v1/users/register` не должен превышать $250 \text{ мс}$, независимо от доступности почтового шлюза.

## 2. Пре-мортем анализ (Pre-mortem Analysis)

*Этот раздел — результат сессии "Pre-mortem" на этапе Idea. Мы смоделировали ситуации, при которых асинхронный подход может сломаться, и продумали митигации до написания кода.*

| Что может пойти не так? (Failure Mode) | Вероятность / Влияние | План митигации (Mitigation Strategy) |
|:---|:---:|:---|
| **1. Потеря события в Kafka**.<br>Продюсер упал до отправки, или брокер потерял сообщение. | Низкая / Критическая | Использовать `acks=all` в Kafka Producer. В БД использовать паттерн **Transactional Outbox**: событие пишется в ту же транзакцию БД, что и `User`, а Kafka Connect (Debezium) сам вычитывает его. |
| **2. Письмо не доставлено (Soft/Hard Bounce)**.<br>Неверный email пользователя или сервер отклонил. | Средняя / Высокая | Консьюмер не должен падать с ошибкой. Hard Bounce помечает `User` статусом `UNDELIVERABLE` (без бана). Soft Bounce использует exponential backoff: $$ t_{retry} = \min(t_{base} \cdot 2^n, t_{max}) $$ |
| **3. Пользователь не получил письмо и жмет "Отправить снова"**.<br>Возникает спам и дублирующая нагрузка. | Высокая / Средняя | API `/resend-verification` проверяет timestamp последнего события в Redis. Rate limit: 1 запрос в 60 секунд на `userId`. |

## 3. Рассмотренные альтернативы (Considered Alternatives)

### Option A: Синхронная отправка + Thread Pool
Создать пул потоков внутри `UserRegistrationService` и отправлять письма в `@Async` методе.
* **Плюсы**: Не требует новой инфраструктуры (Kafka).
* **Минусы**: При перезагрузке сервиса (deploy/crash) все не отправленные письма в памяти теряются. Требует сложной реализации retry и dead-letter queue внутри приложения.
* **Вердикт**: ❌ Отклонено. Нарушает требование надежности.

### Option B: Асинхронность через Spring `@EventListener` (In-process)
Публиковать событие `UserRegisteredEvent` внутри JVM и слушать его в другом бине.
* **Плюсы**: Простота реализации, разделение кода.
* **Минусы**: Те же проблемы с потерей событий при падении JVM, что и в Option A.
* **Вердикт**: ❌ Отклонено.

### Option C: Event-Driven через Kafka + Transactional Outbox
Писать пользователя и событие в БД (Outbox table), Debezium отправляет в Kafka, отдельный микросервис `NotificationWorker` читает и отправляет.
* **Плюсы**: Гарантированная доставка (at-least-once), развязка сервисов, надежность.
* **Минусы**: Усложнение инфраструктуры (нужен Kafka, Debezium, новый воркер), eventual consistency (пользователь может не получить письмо мгновенно).
* **Вердикт**: ✅ Выбрано. Надежность важнее мгновенной доставки.

---

## 4. Принятое решение (The Decision)

Мы выбираем **Option C: Event-Driven через Kafka + Transactional Outbox**.

**Архитектурный контракт (Domain Event):**

```java
public record UserRegisteredEvent(
    UUID userId,
    String email,
    String verificationToken,
    Instant occurredAt
) implements DomainEvent {
    
    @Override
    public String getEventType() {
        return "iam.user.registered.v1";
    }
}
```

**Топология:**
1. `UserRegistrationService` пишет `User` в таблицу `users` и запись в `outbox_events` в одной транзакции PostgreSQL.
2. Debezium стримит изменения из `outbox_events` в Kafka топик `iam.user.registered.v1`.
3. Микросервис `NotificationWorker` (изолированный) потребляет топик, рендерит HTML шаблон и вызывает HTTP API SendGrid.

---

## 5. Последствия (Consequences)

### Positive (Преимущества)
- **Отзывчивость UI**: Время ответа `/register` теперь строго ограничено записью в PostgreSQL ($< 50 \text{ мс}$).
- **Устойчивость к сбоям (Resilience)**: Если SendGrid "лежит", пользователи продолжают успешно регистрироваться. Письма накапливаются в Kafka и будут отправлены, когда шлюз восстановится.
- **Масштабируемость**: `NotificationWorker` можно масштабировать независимо от основного API.

### Negative (Компромиссы и Минусы)
- **Infrastructure Overhead**: Требуется поддерживать Zookeeper/Kraft, Kafka Brokers и Debezium Connect.
- **Eventual Consistency**: В редких случаях (задержка Debezium) пользователь может не получить письмо в течение 1-3 секунд после регистрации. UI должен это учитывать (экран "Письмо отправлено, проверьте почту" вместо моментального редиректа).
